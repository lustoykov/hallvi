# Server Guy testing

**Start here:** `npm run test:dashboard` → [local testing page](http://127.0.0.1:4317).

Run checks, see model usage/CI policy, inspect recent runs, and review saved **live agent eval** answers. Nothing runs just by opening it. Live agent evals and LLM judgments use your subscription, so they start from one confirmation dialog; a live run judges its own answers when it finishes unless you untick that, even when the runner exits with an error after saving them; after Stop, use Judge in the run header. Human verdicts and LLM judgments remain separate records.

- **Run checks:** the suite table shows each suite's scope, model usage, CI policy and its last recorded result. Recent runs list status, scope (selected journeys, cases × repetitions, or judged answers), commit, start time and duration; clicking a run expands its command and bounded output inline. A running check shows a live elapsed time and a Stop control.
- **Choose journeys:** opens a dialog beside the run action, without scrolling the page. Inspect descriptions and select any of fifteen desktop journey groups (fourteen product groups, including reply recovery and Activity, GitHub, durable requests, native history and the Phase 2 Application Contract, plus the dashboard). A group can contain several test cases. The shared catalog and exact test tags live in [browser/journeys.ts](browser/journeys.ts). Smoke still runs just two.
- **Choose live eval cases:** cases are grouped into collapsible categories, with search and a checkbox beside each category name that selects the whole group without expanding it. Only cases with **no saved attempt** are selected by default; **Select failed last time** and **Select rubric changed** pick from saved history, and each row shows its last outcome and date. Archived runs count; failed attempts count as run, but skipped or merely planned cases do not. Use **Select unrun**, **Select all cases**, or individual checkboxes to change the selection. Closing or cancelling keeps manual choices. Each case has its expected behavior and exact input behind a disclosure. Repetitions default to **one**, with 2–5 available explicitly; the footer shows `cases × repetitions = planned answers` before spending confirmation. This history-aware default is dashboard-only; the CLI still runs all cases unless `PI_EVAL_CASES` is set. Saved-run counts are historical, not today's defaults; interrupted runs may have fewer answers.
- **Run case again…:** on an individual answer, runs that case **once** using the current code/case definition and confirmed model settings, even if the original run or picker used more repetitions. Creates a new saved run and never overwrites old answers/reviews; like any live run it is judged automatically after a successful finish unless you untick that in the confirmation. Also available when the case failed before replying; removed cases cannot be rerun.
- **Eval runs:** the topbar switches between **Run checks** (`/`) and **Eval runs** (`/evals`); the Eval runs link carries a count of answers needing attention, and **View saved runs** under Live agent evals opens the same page. Direct links, refresh, new tabs and browser Back/Forward work. In-page route changes preserve unsaved review drafts and selections. The sidebar lists runs (newest first, archived ones in a collapsed group) and the open run's answers; the main column shows one answer with Previous/Next and J/K navigation. Repetitions of a case sit together. **Run evals** generates answers and, by default, judges them as soon as the run finishes with the same model. The run header's **Judge** button covers older runs: it targets the answers the current judge policy has not judged yet, or everything again once all are judged.
- **Judge-first triage:** the **Attention** filter is the default: unjudged answers, failures and uncertain judgments. **Failed**, **Cleared**, **Reviewed** and **All** are the other filters, each with its count. The run header shows one bar of the whole run's triage plus a line such as “11 need attention · 4 LLM-cleared · 3 of 16 human-reviewed · judge agreed 2 of 3”; the last part counts answers where both you and a current-policy judgment exist, and each such answer says whether the judge agreed with you. In the queue, not-judged answers show a quiet dot and every other status a labeled chip; the open answer shows one status line with its triage label and reason. Current-policy judge passes clear only with passing recorded code checks; missing evidence, errors and old-policy advice cannot clear an answer. A human pass is labeled separately; neither a model nor a human pass hides failed code checks. Triage is derived, never written over original results or human verdicts.
- **Spot-checking the judge:** open the **Cleared** filter now and then and grade a few answers yourself. Before trusting clearance, compare the judge with your own labels on a small representative set including known bad answers; uncertainty reported by the judge does not catch confidently wrong passes. See the [acceptance guide](../docs/testing/phase-one-acceptance.md#calibrating-the-judge).
- **Judging:** **Judge** in the run header covers the run, labeled with what it will do (the answers the current policy has not judged, or everything again); With nothing unjudged, the same button re-judges what the current filter shows (“Judge these 2 again…”), or the whole run under All (“Judge run again…”). **Judge this answer…** (or **Judge again…**) inside the LLM judgment box judges just that repetition. Answers you graded yourself are not counted as unjudged; judge them one at a time if you want the LLM's opinion for calibration. The judge grades against the casebook's current rubric wording and records it; after a rubric edit, earlier judgments keep their verdict but show an “Older rubric wording” flag in the judgment box, and the answer shows the current wording with the saved one behind “Wording changed since this run”. It opens the same one-step confirmation (count, model/effort behind Change, Start). One isolated judgment per saved answer, sequentially; failure/timeout stops later judgments and keeps earlier verdicts. No human approval or app rerun.
- **Archive run / Restore run:** move the **entire open run** into or out of the sidebar's Archived runs group, independently of the open answer. Archived runs leave the pending count but stay readable and reviewable; new runs start active. Evidence and verdicts are untouched; archiving is not approval. Failed/empty runs can also be archived. The private `run-state.json` stores one boolean bound to the original results hash. No automatic age-based archiving.
- **Your verdict:** one click on **Pass**, **Fail** or **Discuss** (or the P / F / D keys) saves it and moves to the next answer in the queue. No name or reason is asked: the record carries your local username, and **Add a note** is optional. The button matching the saved **LLM judgment** carries a small LLM tag; the judgment never fills in or changes your verdict. The header's human-reviewed count never includes LLM clearance.
- Each new dashboard run records its shell-quoted command and explicit runner options with its output. Inherited environment variables and credentials are not recorded.

## Files

```text
tests/
├── application/        Application tests suite (Vitest)
│   ├── unit/           Isolated rules, routes and components; external boundaries mocked
│   ├── integration/    Real SQLite, filesystem, HTTP or subprocess boundaries
│   └── vitest.config.mjs  Selects only these two folders; never live evals
├── browser/            Browser journeys + tagged smoke subset (Playwright)
├── browser-fixtures/   Synthetic Pi, GitHub and login adapters
├── fixtures/           Synthetic repositories, GitHub tree/contents responses and the scripted contract builder
├── evals/              Live Server Guy cases/checks/runner; saved-answer judge
├── dashboard/          Separate loopback-only Node server and static UI
└── results/            Private generated output; gitignored
    ├── runs/           Dashboard command history and bounded logs
    ├── browser-report/ Playwright HTML report
    ├── browser-artifacts/ Traces and screenshots
    └── evals/<run>/    results.json, review.md, reviews/*.json, run-state.json
```

The product's acceptance cases and dated verification evidence stay in the single [Phase 1 acceptance guide](../docs/testing/phase-one-acceptance.md). Implementation order stays in [ROADMAP.md](../ROADMAP.md). This file is an index, not another plan. Temporary fixture apps and eval databases live under `/tmp/server-guy-*` and are deleted after normal runs (only a hard kill can leave one behind); their results belong here. Do not commit private outputs or credentials.

## Suite explanations

The **How it works** page (topbar) compares the four suites in one table and also holds the AI-usage notes and the file map; reading it never starts a test. The Run checks table itself stays a plain table of actions. Every suite uses the same fields: execution, real dependencies, mocked dependencies, database isolation, checks/review, and what passing does not prove. **Code & saved output** lists the command, source files and artifact locations. The copy lives in [dashboard/suite-guides.ts](dashboard/suite-guides.ts), separate from execution logic.

The folders match the dashboard suites: **Application tests** → `application/`, **Browser smoke / Browser journeys** → `browser/`, **Live agent evals** → `evals/`. Browser smoke selects tagged tests from the same browser suite, not a separate folder. `dashboard/` is the testing tool, not another test suite; `browser-fixtures/` and `test-database.ts` are shared support.

Application tests are split by their strongest boundary. `unit/` calls isolated rules, routes or components with external dependencies mocked; `integration/` exercises real SQLite, filesystem, HTTP or subprocess interactions. A file containing both stays under integration. These are both deterministic, no-model suites—not live evals. Database setup still belongs to each test file; moving a file does not change its reset policy.

Durable request coverage starts in [application/integration/pi-runs.test.ts](application/integration/pi-runs.test.ts): enqueue/claim/finish, cancellation settlement, linked retry, scoped Run context and real worker crash/restart. [application/integration/pi-sessions.test.ts](application/integration/pi-sessions.test.ts) covers real native files, identity, locking and missing-history detection; [pi-decisions.test.ts](application/integration/pi-decisions.test.ts) covers scoped reads and guarded writes. [application/unit/pi-stream.test.ts](application/unit/pi-stream.test.ts) checks reconnectable snapshot delivery. Browser fixtures run a disposable Next.js app **and worker**, including the real Pi adapter, native SDK and tools; only the model/provider is synthetic. Stopping the fixture stops both and deletes its database and native files. Live evals call the same enqueue/worker code through [execute-pi-turn.ts](execute-pi-turn.ts), without a web server or separate worker process, and count model/tool-loop rounds and compaction starts (not a billing estimate).

Run either subset without a new runner: `npm test -- tests/application/unit` or `npm test -- tests/application/integration`. Existing `test:e2e` commands keep their names and now point at `browser/playwright.config.ts`.

Phase 2 coverage starts in [application/integration/phase-two.test.ts](application/integration/phase-two.test.ts): the explicit transition and its refusals, read-only completed phases, deterministic inspection outcomes, and the real SDK tool loop reading pinned files and proposing, rejecting, cancelling, retrying and revising the Application Contract, plus invalidation, isolation and removal. Unit files cover the profile resolution, the contract validator and gap report, every Phase 2 check reason, and the bounded GitHub reads with deny list and redaction. [fixtures/repositories.ts](fixtures/repositories.ts) holds the synthetic repository trees shared by all of these, the disposable browser app and the eval seeds; nothing in them is the private `todo-fastapi` layout.

Seven cases in **Conversation memory & compaction** cover older saved requirements, cross-chat updates, correction versus addition, implicit constraints after a missed query, and a cancelled proposal before/after compaction. Six explicitly trigger compaction; the remaining case checks a cancelled proposal without compaction. [evals/native-scenarios.ts](evals/native-scenarios.ts) seeds clearly synthetic previous history/usage in real native sessions and lowers the retained-history setting for inexpensive real auto-compaction. The new reply, lookup/tool loop, summary and final transaction are real. This tests behavior, not production context-window capacity. Native tool calls/results and compaction summaries are retained in `results.json` as `nativeEvidence`, included in saved-state details and supplied to the optional judge. Temporary databases and native histories are deleted after reports are saved; no live user conversations are copied.

Four cases in **Defaults and requirements** check that the model balances ordinary operating goals without a ranking questionnaire or unnecessary saved Decisions, while still recording an explicit hosting budget or EU data-residency requirement. The native addition case also checks that a new residency constraint preserves an existing saved choice. These are live behavior checks, not just assertions that the system prompt contains the right words.

## Commands

| Task | Command | Model calls |
| --- | --- | --- |
| Testing dashboard | `npm run test:dashboard` | None until explicit live start |
| Application unit + integration tests | `npm test` | None |
| Interactive Vitest | `npm run test:ui` | None |
| Two desktop smoke journeys | `npm run test:e2e:smoke` | None |
| Full desktop suite | `npm run test:e2e` | None |
| Interactive Playwright | `npm run test:e2e:ui` | None |
| Saved browser report | `npx playwright show-report tests/results/browser-report` | None |
| Thirty-seven real agent eval cases | `SERVER_GUY_LIVE_EVALS=1 npm run eval:pi` | ChatGPT subscription via configured Pi |
| Judge saved answers | Automatic after a dashboard live run, including one whose runner failed after saving answers; otherwise Eval runs → Judge in the run header | Separate opt-in Pi session per answer |

Install Chromium once with `npx playwright install chromium`. Desktop only. Browser scenarios launch disposable Next.js fixtures on 3180+, never use/reset the app on port 3000 and block external browser requests. Their synthetic model responses prove UI/state behavior, not model quality.

GitHub browser tests exercise the real connection routes, coordinator, repository adapter and SQLite; only GitHub API/device responses and CLI credential discovery are replaced. Run this group alone with `npm run test:e2e -- --grep @journey-github-connection`. It covers explicit reuse, device-code success/cancellation/denial, permission failure/recovery and disconnect/re-verification. The unit/integration cases cover expiry, revocation, changed credentials, exact repository IDs, races and secret redaction without live accounts.

Three live eval cases test how Pi explains GitHub evidence: connected but denied repository access; an old passing check after switching GitHub logins; and a passing repository read that does not imply a code audit, passing tests or deployment. Their connection, observations and previous chat are synthetic records in the scratch directory; Pi's answer and the application's check computation/transaction are real. The shared seed is in [evals/seed-phase-one.ts](evals/seed-phase-one.ts). Select just those cases in the dashboard, or run `SERVER_GUY_LIVE_EVALS=1 PI_EVAL_CASES=github-connected-not-readable,github-reconnected-stale-success,github-verified-not-audited npm run eval:pi` (three turns by default). No GitHub requests or real GitHub credentials are involved; real Pi calls use your configured subscription.

Seven cases in **Application status** check that Pi reads current application state through the scoped `get_application_status` tool only when an answer depends on it, now that no application summary is injected before each reply. Two cases (an acknowledgement and a conceptual question) must answer without a lookup; five must look status up in the current Run: blockers, whether the repository is still readable (a two-day-old recorded check, not a live recheck), an earlier conversation that claimed all checks passed while the latest check failed, an Approval Mode that changed since an earlier answer, and readiness versus deployment. The greeting and GitHub cases carry the same lookup expectation. Stale-history cases seed an explicitly synthetic earlier `get_application_status` exchange in the real native session; the recorded `nativeEvidence` shows which tools the live Run actually called. Run them with `SERVER_GUY_LIVE_EVALS=1 PI_EVAL_CASES=status-thanks-no-lookup,status-concept-no-lookup,status-blocking-next-step,status-repository-still-readable,status-stale-check-history,status-approval-mode-changed,status-ready-not-deployed npm run eval:pi`.

Eight cases in **Application Contract** check Phase 2 judgment: which files to read, what to quote as declared, what to label inferred or leave unresolved, what to hand to Phase 3 as conformance work, when a contradiction needs the engineer's decision, that README text addressed to the assistant is data, that an unsupported repository gets an explanation instead of a contract, and how a correction or a re-inspection at a new commit revises the contract. They seed a Phase 2 workspace with a synthetic inspection and saved reads of a fixture repository; `read_repository_file` is served from those records and the GitHub API is blocked. Automatic checks verify whether a contract was committed, its recorded conformance items and blockers, and that no forbidden value was called repository-declared; provenance itself is enforced by the commit. Run them with `SERVER_GUY_LIVE_EVALS=1 PI_EVAL_CASES=contract-conforming,contract-missing-health,contract-localhost-bind,contract-sqlite-contradiction,contract-malicious-readme,contract-unsupported-django,contract-user-correction,contract-stale-commit npm run eval:pi`. They were added without being run; see the testing guide for what has actually been run.

CI runs Vitest, lint, TypeScript, build and **two** browser smoke journeys. Full desktop coverage is manual through GitHub Actions' `full_browser_suite` option. Neither uses model credits; hosted CI uses Actions minutes. Real model evals and judgments remain local and opt-in. See the [workflow](../.github/workflows/checks.yml).
