A passing check is not a meaning verdict.

A separate, opt-in Vitest runner tests the existing chat path with real Pi and synthetic application data. It checks the stored result, then leaves the meaning of the answer for a human to review.

What changes in this PR

Eight fixed cases, an opt-in runner, exact state assertions and a review sheet. Ordinary npm test remains offline. The runner is sequential, stops further turns on Pi runtime/provider failure, and never switches models or billing modes.

Example: “Is lowest cost the right priority?” must create no Decision. A valid schema alone cannot tell us whether Pi mistook a question for a commitment.

What stays outside

Your application database and transcripts are not read. No GitHub calls, new runtime, worker or production UI flow. The existing OAuth file remains the credential source; normal Pi refresh may update it. Tokens are not copied into reports.

The runner records accepted proposals, not a full SDK trace. Model quality is not certified by eight examples or by a second model's opinion.

Developer entry point: npm run test:dashboard opens a separate localhost page for test runs and saved-answer review. The optional isolated Pi judge adds advisory records beside human reviews; it does not replace them. Desktop Playwright checks use synthetic providers, separate from this live-model flow.
