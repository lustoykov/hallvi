# Native Compose: facts the current consumers need

10 September 2026. First design proof for the [requirements-driven architecture](requirements-driven-deployment.md). This is a consumer inventory and configuration comparison, not a new service schema. The existing custom-plan executor still runs production deployments.

## Consumer-fact ledger

“Derived” means read from the retained resolved native configuration. “Observed” means established by a timestamped execution or inspection. “Recorded” means information requiring a separate source, decision or operational record. A source configuration does not establish runtime behavior.

This accounts for the current plan's image/build, environment/input, configuration-file, service/dependency, volume/protection, HTTP/readiness/check and descriptive-summary families. It is not a claim that these consumers have already migrated. The proof found no need for another executable service language; it did identify facts that still require records outside Compose.

## Complexity comparison

This first slice retires **zero** deployment-schema/renderer/validator lines and introduces **zero** new production deployment fields. It adds the native tool execution environment and runs a comparison. Claiming that the executor is already simpler would be premature.

The following PR should measure the custom admission, rendering and validation code actually removed against the native-artifact admission and effect-comparison code added. A new inventory must remain a projection; it must not grow into another configuration authoring format. Concrete preservation requirements in the table decide whether the replacement is adequate.

## Recorded Paperless comparison and correction

Pi ran through the native workspace tools with the configured `openai-codex/gpt-5.6-sol` model at high effort. Inputs were the pinned upstream Paperless Compose/env files and the existing trial's recorded plan rendered with synthetic credentials. The same Compose 2.40.3 resolver normalized both inputs with project name `proof-comparison`; no stack was started.

The first candidate validated but was not an equivalent update. It retained upstream consume/export bind folders instead of the two recorded named volumes and introduced separate broker/database networks. Those were model-chosen configuration differences, not new core branches. We compared the actual resolved configurations and supplied the specific mismatches back to Pi in a second run, requiring preservation of every existing mount and the existing network. Pi corrected the native YAML without a new approval or custom service language.

The corrected native and legacy resolved JSON are byte-for-byte identical. SHA-256 for both is `2259da827b85c2effe00c208aa605a3792cd6b976207fa85243f39880029b37f`; corrected native YAML SHA-256 is `3651dde047d4ac0c856a6ac425a8ddd75f016d106faccd84dc6fa03298d7c0b6`. The comparison preserves all three service identities, six named volumes, image references, exposure, dependencies, environment and baseline network configuration. PostgreSQL remains the baseline's mutable `postgres:18` reference; this does not establish its running image digest or rollback safety.

A second correction concerned HTTP: Compose publishes the application port, but the current executor separately configures the Hetzner firewall for controller-only access (`deployment-executor.ts`). Missing firewall rules in YAML are not evidence of missing provider protection. This is a concrete example of necessary management facts outside native configuration.

This was a human-checked feedback pass through Pi's native tools. It does **not** demonstrate a newly implemented production native-artifact authorization loop. The following executor PR must return these comparisons as generic tool feedback under the managed execution boundary, rather than rely on a person reading a diff.

## Generalization requirement

The production workspace receives an application/run identity and source snapshot; it contains no Paperless, Grafana or other application-name execution branch. Paperless-specific commands, filenames and expected behavior belong in its proof inputs, not in the reusable runtime.

The intended loop for every application is: inspect its configuration and records; author native artifacts; receive native diagnostics and generic effect/identity comparison results; correct within the task; apply through managed execution; inspect the actual outcome. Target identity, mounts/access, network effects, private inputs and recorded outcomes are general facts. They must not become Paperless-specific validators or a new fixed topology/schema. Capability gaps return to Pi as such; they are not disguised as application incompatibility or solved by pretending a check passed.

As a separate configuration-capability check, the same native tool path validates a synthetic worker-only stack with two independent build contexts, a shared writable/read-only volume and no `app` service or HTTP endpoint. This check is directly driven through the workspace adapter, not another model or deployment run. It tests that the tool surface accepts a materially different arrangement; it does not claim the current production deployment executor can already deploy it.

**Smallest next implementation:** select and retain a native artifact bundle plus its resolved snapshot, derive only the facts the existing managed executor needs, and return generic mismatch/diagnostic feedback to Pi. Preserve old release readers. Exercise the corrected existing-app case and the worker-only case against that path before claiming general native deployment support.
