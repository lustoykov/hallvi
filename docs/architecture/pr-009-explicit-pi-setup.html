Architecture · PR 9 · Pi runtime boundary

One visible setup path, one explicit Pi configuration

Prototype A is the selected desktop login screen. Reuse snapshots Pi’s displayed preferences and shares its credential file. A separate login keeps the chosen model draft and activates its own file only after OAuth succeeds. Global Pi preferences stay untouched.

Visible setup

  • Read-only preview reports provider, model, effort, and credential presence. No token refresh or provider request happens during detection.
  • Reuse skips OAuth and shares Pi’s existing auth.json. Separate login writes .server-guy/pi-auth-<login-id>.json, then atomically activates it in pi-settings.json. Failure or cancellation keeps the old connection.
  • Only ChatGPT subscription OAuth is reusable. API keys, other providers, custom models, and command-based credentials are not imported.

Enforced at runtime

  • askPi() requires the saved pi-settings.json choice and passes its model and effort explicitly.
  • Global model preferences never change. Shared OAuth token refresh is allowed only after consent. Model/effort combinations are validated on save and before each turn.
  • Readiness is local presence, not a provider probe. Access, refresh, and usage errors appear on send.

Still deferred

No GitHub OAuth, durable Pi Run, worker, SSE, transcript compaction, API-key billing, or Phase 2 behavior. A live account test still needs the user to approve OAuth.
