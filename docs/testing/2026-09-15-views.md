# Deployment, History and command output

15 September 2026. Branch `claude/cp5-deployment-history-logs`, from main
`6177177`. Checkpoint 5, plus the four items deferred from checkpoint 2.

Synthetic throughout. A `Scenario · four releases` fixture carries a first
release, a second, a failed update, a retry that worked, a backup, and a
private-access failure that was resolved.

## What the three pages actually did

Established by reading the projections before changing anything:

| | What it read |
|---|---|
| **Deployment** | The *newest* deployment record, whatever became of it, and its commands as phases. No list of earlier releases — so a failed update replaced a release that had been serving for days. |
| **History** | Every saved record **plus every execution**, flat. One deployment produced a dozen rows that each said a command had run. |
| **Logs** | Every execution that has output — so History already contained everything Logs showed, with a title instead of a body. |

And **no runtime-log capability exists**: no tool in the product retrieves an
application's logs. What Logs called a log was Server Guy's own command
output.

## What changed

**Deployment leads with what is running.** A new projection separates three
questions that had been one: what is running (the newest release a check
proved), what happened last (the newest attempt), and what else has run. It
has a third outcome besides deployed and failed — something ran and nothing
established what came of it — where the honest answer is that the current
state is unconfirmed, *not* the previous release, because a container replaced
by something that would not start is not still running the old image.

Previous releases are a list. Opening one shows what changed, the source, what
was checked and Pi's note. The panel carries no fact row: the release story
below it already holds the running image, its digest, the revision, the server
and the tunnel's two ports, and a summary above it would be the same facts
twice.

**History records what happened.** A command that succeeded is evidence on the
event it produced. Four kinds still earn a row, because none is evidence of
anything: waiting on the reader, failed, interrupted, and declined — that last
because a history that drops the owner's own decisions is a history of what
Server Guy chose. Records earn a row when they are things that happened:
releases, access changes, backup and restore results, credential and domain
changes, and any failure.

On the fixture that is **9 events where the old projection produced 20**.

**"Logs" is "Command output".** Named for what it holds, with the empty state
pointing anyone hunting application logs at the conversation. It also carried
a *fourth* copy of the "where did this run" table; it reads the shared one.

**A failure says what failed.** Where a command failed, the line gives the
machine, the exit code and the last line of its output that says something.
The control follows the failure: a command that rejected its input offers
*Ask what went wrong* (the question goes into the composer); a dropped
connection offers *Try again*. A run's own `error` stays internal — it is
runtime text and the product had already decided that, guarded by a test.

**A busy local port is bookkeeping.** The tunnel tool now says so in as many
words, and says that a port in use on the *server* is a different question
that goes to the owner.

## Not decided here

**Where History and command output sit in navigation.** `hideable` means
"hide until something records this", so a populated History is promoted back
to primary by design — the flag is not a demotion lever. Making either
permanently secondary is part of the navigation arrangement, and six
arrangements are preserved on `prototype/navigation-directions` for the owner.

**Two leads on Deployment.** The running-release panel and the release story
below it both open with a headline. Resolving that means choosing Deployment's
final shape, which is the open decision.

**Nothing records which command produced which record.** Evidence is attached
by adjacency and the page says so. A minimal explicit association written at
save time is the real answer, and it is a capability change rather than a
layout one.
