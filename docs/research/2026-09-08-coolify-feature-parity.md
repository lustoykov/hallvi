# Coolify comparison — former parity proposal

> Dated research/reference, not an active requirement or implementation plan. Current scope is in [Product](../../PRODUCT.md) and delivery is in [Roadmap](../../ROADMAP.md). Recheck version-sensitive facts before use.

Researched: 2026-09-08. Primary-source documentation review, not a hands-on Coolify acceptance run. Product direction is confirmed; Server Guy implementations below are proposed requirements, not shipped capabilities. [PRODUCT.md](../../PRODUCT.md) owns positioning, the [capability specification](../specs/self-hosting-capabilities.md) owns support criteria, and [ROADMAP.md](../../ROADMAP.md) owns delivery status and order.

## Status of the proposal

The original broad feature-parity commitment was withdrawn on 9 September. Retain the comparison below as dated competitor research; select only capabilities serving the current single-instance stack. It neither expands scope nor schedules implementation.

## Findings that change the plan

Coolify already removes substantial work: automatic source builds, container deployment, proxy/TLS configuration, scheduling, backups and event notifications. The opportunity is to perform the remaining cross-system configuration and investigation, then prove the desired outcome. The matrices below distinguish documented automation from documented setup burden rather than treating Coolify as entirely manual.

There are two particularly relevant limits in the main documentation: rolling updates exclude Compose deployments, and experimental Sentinel metrics exclude Compose and service-template deployments. Server Guy's Compose-first path must explicitly design its release continuity and per-service observability instead of inheriting a generic “Coolify supports it” checkbox. [Rolling updates](https://coolify.io/docs/knowledge-base/rolling-updates), [Sentinel and metrics](https://coolify.io/docs/knowledge-base/server/sentinel).

Coolify already exposes an API and MCP. “Has an agent” is insufficient differentiation. Server Guy should own the continuing goal, missing-input resolution, operational evidence, recovery and user-tailored UI. The MCP documentation is internally inconsistent about write support; see C20 rather than claiming Coolify's assistants cannot act. [API authorization](https://coolify.io/docs/api-reference/authorization), [MCP](https://coolify.io/docs/integrations/mcp).

Provider-choice follow-up: Coolify also documents provider provisioning, not only bringing an existing server. The main API exposes [Hetzner server creation](https://coolify.io/docs/api-reference/api/hetzner/create-hetzner-server); its [next provisioning guide](https://next.coolify.io/docs/core/infrastructure/servers/provision-cloud-server) adds Hetzner/DigitalOcean/Vultr selection, token/key setup and an explicit billable creation action. Check installed-version coverage for the latter. C08 should therefore be read as including both existing-host connection and provider creation. Server Guy's proposed improvement is application-specific recommendation, setup and verification, not the novelty of a provider picker.

## How to read the comparison

- **Main docs** means `coolify.io/docs`, the primary comparison baseline. It still contains version-specific and experimental material; this is not a guarantee for every installed version.
- **Next docs** means `next.coolify.io/docs`, a separate documentation surface. It supplies useful detail but does not, by itself, establish which released binary implements that detail. Such rows are marked and need installed-version/source verification before asserting exact parity.
- A Coolify **Application** using a Git-backed Compose build pack and a **Service** created from a Compose definition/template are distinct paths. The main CI guide distinguishes Git-integrated Applications from directly supplied Services. Do not extend every Git feature to a Service simply because both use Compose. [CI/CD resource distinction](https://coolify.io/docs/applications/ci-cd).
- “User work” below is visible in documented flows. APIs or an existing integration may automate parts of it; the claim is not that no automation is possible.
- Priority is a research recommendation: **Foundation**, **Care**, **Expansion**, or **Deferred by current scope**. It is not a second implementation checklist.

## Concrete agent-first flows

These are proposed Server Guy interactions, not claims of current implementation or additional mandatory UI stages.

**“Deploy this repository on my VPS.”** Inspect repository and host in parallel where independent. Reuse Dockerfile/Compose if suitable; prepare missing configuration and prerequisites. Ask inline for a missing external secret or inaccessible account. Execute within the accepted goal. Show the resulting services and address while checks run; finish with the exact serving revision, a working external check and any unprotected state. Details expand on demand.

**“Make sure the database is backed up.”** Find its engine and storage, explain one sensible destination/schedule with an override, establish available storage access, run the backup and off-host transfer, then restore a disposable copy. The dashboard separately shows newest backup, newest off-host copy and last restore test. If transfer fails, preserve the local copy and report the unfulfilled off-host protection; do not label the whole request done.

**“Use my domain and add a CDN if it helps.”** Discover current DNS and application response types. Reuse existing domain ownership/provider instead of asking the user to pick a vendor list. Change the appropriate records, origin/proxy/TLS and cache policy; test an eligible asset and a sensitive/dynamic route. If the registrar requires a user-only action, render that single instruction inline and resume verification afterward.

**“Release the latest passing commit.”** Resolve the eligible candidate once, connect its checks to the image digest, apply the release and existing migrations, then test the result. A failed migration or post-release check keeps the release visibly unresolved. Investigate the evidence, perform authorized operational recovery where compatible, or prepare a coding-agent packet. Do not silently substitute a newer commit. After controller interruption, inspect migration history and reconcile ambiguous completion before retrying; an execution receipt can be lost after the database has changed.

**“What is filling my disk?”** Measure directories, volumes, images and logs; identify ownership and trends; propose a targeted change with its effect. Apply authorized retention/cleanup and remeasure. Offer a disk UI Plugin connected to the same real measurements, with persistent preferences and explicit background-collection lifecycle.

## Server Guy implementation baseline

Read-only code inspection on 2026-09-08 in the integration worktree based on PR #21 commit `c7ed574`; no runtime tests were rerun for this documentation research. The [roadmap parity table](../../ROADMAP.md#compatibility-gates) owns ongoing status.

- The current execution profile is one FastAPI/uv application with PostgreSQL, rather than general Compose or packaged-software execution. [Profile definition](../../src/server/application-profile.ts)
- Repository inspection/preparation and GitHub publication provide reusable foundations. They remain coupled to the older phase workspace model. [Preparation](../../src/server/preparation.ts), [GitHub publication](../../src/server/github-publication.ts)
- Dockerfile builds use an ephemeral local rootless builder; the application preview is a local verification lifecycle. Neither establishes deployment to a user's remote server. [Image build](../../src/server/application-image.ts), [Local preview](../../src/server/application-preview.ts)
- Pi is configured with explicit tools and disables ambient extensions. Its present integration is not a general remote host operator or the proposed UI Plugin runtime. [Pi configuration and tools](../../src/server/pi.ts)

The immediate gap is therefore real remote execution and ongoing operations, as well as broader application support. The existing evidence/state machinery should be reused while the accepted shell is integrated. The prototype's provider choices, releases and operational charts remain simulated evidence of interaction design.

## Acceptance probes and measures of reduced work

Use the existing [compatibility cases](../testing/self-hosted-compatibility.md): a source application, Grafana, Prometheus, the combined monitoring stack, and Coolify on an isolated test host. They test different combinations of images, config files, volumes, networking and host preparation. Success deploying one named tool must not imply its backup/update/recovery machinery also works.

For each relevant capability, record:

- User decisions and credential/account interventions; distinguish necessary authority from avoidable configuration work.
- Manual files, copied commands and provider-dashboard steps required after granting access.
- Verified outcome and evidence identity: host, source/image revision, service, configuration and observation time.
- One meaningful failure/recovery path, including missing access or controller interruption where applicable.
- Ongoing operation with chat closed; backup/monitoring freshness and unavailable states.

The goal is fewer avoidable interventions **while preserving user control and improving verified completion**, not zero clicks as an isolated metric. A retained terminal is compatible with agent-first operation; routinely requiring it for documented everyday setup is not the target experience.

## Version-sensitive findings and unresolved checks

1. **MCP contradiction:** the main page's introduction and permission advice say read-only, but its available-tools section names lifecycle/deploy/cancel tools requiring `deploy`. This report does not resolve which binary first ships them. Inspect the installed tool catalogue and exact release/source before making a negative competitive claim. [MCP](https://coolify.io/docs/integrations/mcp)
2. **Backup breadth:** the main page foregrounds scheduled PostgreSQL/Coolify backups while next documents more engines, Service credentials, retention and restore UI. Treat next as evidence to test, not grounds to claim either that these features are absent or universally released. [Main backups](https://coolify.io/docs/databases/backups), [Next backups](https://next.coolify.io/docs/databases/backups)
3. **Compose scope:** no rolling updates and no Sentinel metrics for Compose/service templates are explicit main-doc limitations. Verify against a named version before publishing comparison marketing; they already justify targeted Server Guy acceptance. [Rolling updates](https://coolify.io/docs/knowledge-base/rolling-updates), [Sentinel](https://coolify.io/docs/knowledge-base/server/sentinel)
4. **Post-deployment hooks:** next Dockerfile docs say failed post-deployment commands do not reverse a successful deployment status. Check release-specific behavior. Independently, Server Guy should keep an intended release unresolved when its required migration/verification failed. [Next Dockerfile](https://next.coolify.io/docs/applications/builds/dockerfile)
5. **Provider and platform breadth:** this is a practical capability baseline, not every template, framework, API endpoint or enterprise feature. Do not infer unsupported providers, database engines or protocols merely because they were not investigated here. Further cases can extend the inventory without redefining the positioning.

No infrastructure was installed or changed for this research. No current Server Guy feature parity is claimed.
