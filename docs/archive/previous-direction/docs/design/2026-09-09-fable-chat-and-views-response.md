# Fable: chat and stable views handoff

> Archived reference, 9 September 2026. Preserved for evidence and migration; instructions and unchecked lists below are historical, not the current product plan. See [Product](../../../../../PRODUCT.md) and [Roadmap](../../../../../ROADMAP.md).

Model: claude-fable-5-1. Read-only briefing session: `1096adeb-8948-4f8d-9837-15d86ea396ad`. No implementation or worktree creation was requested in this turn.

Read the brief, the navigation note, the design system, the four shell components and five screenshots.

**Actual state.** The shell has two mutually exclusive modes. A conversation shows with a 320px right panel that repeats Overview facts, the deployment panel and legacy preparation details. Selecting any destination hides the chat column entirely and renders the section full width, so today no stable view can be seen beside a conversation. Overview is the section shell plus the legacy Record inspector stacked underneath. Sections read only the deployment record and the operator view. There is no application-level notion of "this section changed because of that action", so nothing can drive an updated indicator, an action receipt, or a distinction between proposed, executing, verified and failed state in a view. Database, Backups, Observability, Domains and Variables are honest placeholders. Mobile already turns destinations into a scrolling row above conversations.

**Most important unresolved decision.** Whether a stable view may be open beside a conversation at all. Everything else follows from it. If views and chat stay exclusive modes, the only bridge is receipts in chat plus quiet indicators in navigation, and the right panel must either become a real contextual inspector or go. If a view can sit beside chat, the right panel is replaced by the pinned view and the question becomes who controls it. That choice also decides mobile behaviour, since a pinned view and a drawer are the same thing at 390px.

A second decision is shared by every option and I would settle it first: a per-application change record keyed by destination, carrying state (inspected, proposed, executing, verified, failed), originating conversation and action, and timestamp. Overview, receipts, indicators and pinned views all read from it. Without it, each option is only a layout.

**How I would run the comparison.** Snapshot the current tree into an isolated worktree per the brief, then build one clearly labelled simulated fixture on a separate port that replays a scripted timeline for the shared scenarios: disk inspection, backup configuration with access request, approval, progress and verification, failed backup, leaving and returning via Overview. Keep the chat column mounted rather than hidden so scroll position and draft survive. Implement the three options as variants selected by a query parameter, reusing the existing section components and data. Capture desktop and 390px screenshots at each timeline step with Playwright, then score each option on the brief's criteria in one table. My working hypothesis is a hybrid: receipts and indicators as the baseline, plus a user-pinned view, with the current right panel removed. The fixture should test whether that holds.
